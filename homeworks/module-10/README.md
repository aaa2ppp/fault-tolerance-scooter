# 🛴 Модуль 10. Кейс: «Скидка под нагрузкой»

## 🎭 Контекст

Компания **ScooterFlow** развивает сервис аренды самокатов. В личном кабинете пользователь видит персональную скидку: **0%** за 0–9 завершённых поездок, **10%** за 10–49 и **20%** за 50 и больше.

Продолжаем историю из [модуля 4](../module-4/README.md). `Profile.GetDiscount` получает количество завершённых поездок через `Pricing.GetCompletedTripsCount` и рассчитывает скидку.

```text
Пользователь → API Gateway → Profile → Pricing → PostgreSQL Pricing
                               │
                               └── Valkey Cluster: кеш скидки
```

Profile уже кеширует подтверждённую скидку. При попадании он возвращает скидку и число поездок из Valkey. При промахе проверяет профиль в PostgreSQL, запрашивает актуальный счётчик в Pricing и рассчитывает скидку. Пользователь сразу получает ответ, а горутина записывает снимок в Valkey командой `SET` с TTL **10 минут**.

Если сразу после записи пользователь завершит десятую поездку, Pricing учтёт десятую поездку, а Profile продолжит показывать прежние 0% до истечения ключа. Задача команды — обновлять видимую скидку по событию об изменении статистики.

Ключ скидки — `user:{UUID}:discount`. Фигурные скобки сохраняются как hash tag пользователя. Стенд включает Valkey Cluster и Kafka.

Скидка в этом задании служит для отображения в личном кабинете. Подписка пользователя и сохранённая стоимость поездок остаются отдельными данными.

### 🎯 Бизнес-требование

Получение скидки должно быть быстрым и стабильным, даже когда Pricing работает плохо. Используйте ограничения времени и fallback из модуля 4. Явно обозначайте устаревшие данные и fallback. Кешировать 0% можно только при подтверждённом результате расчёта.

## 🧰 Подготовка стенда

Из корня репозитория выполните:

```sh
make cli
./bin/scooterctl up --timeout 15m
./bin/scooterctl status profile
./bin/scooterctl valkey CLUSTER INFO
```

В выводе `status profile` у двух Pod должно быть `READY true`. В выводе Valkey проверьте `cluster_state:ok` и `cluster_slots_ok:16384`. У Valkey три основных шарда и по одной реплике на каждый. Gateway распределяет вызовы между готовыми репликами Profile.

Путь чтения начинается в [Get адаптера скидки](../../services/profile/internal/infrastructure/adapter/discount/read.go). В [конфиге Profile](../../services/profile/config/config.yaml) задано `cache.ttl: 10m`. Попадания в кеш сохраняют исходный срок истечения ключа. Топик `user-discount-invalidate.v1` подготовлен для задания 2.

| Пользователь | Начальные данные | Для чего нужен |
| --- | --- | --- |
| `704137fe-93b3-4113-8e09-ed1df4d0e0ea` | 12 завершённых поездок, скидка 10% | Нагрузка на один ключ |
| `10000000-0000-4000-8000-000000000001` и `…000002` | По 9 поездок, скидка 0% | Десятая поездка до и после реализации инвалидации |
| [1000 пользователей](users.json) | Отдельный профиль на каждый UUID | Нагрузка на разные ключи |

Для ручных запросов откройте [Swagger UI](http://localhost:18080/docs/index.html) на своей машине. Для повторяемой нагрузки используйте `scooterctl load`. Он запускает Framer, показывает каталог отчёта и сохраняет в нём `summary.json` с p95, p99 и числом ошибок. Попытки RPC из Profile в Pricing видны в `./bin/scooterctl logs profile --outgoing -f`.

## 1️⃣ Один горячий ключ и singleflight

Когда у популярного профиля истекает TTL, в логах Pricing появляется всплеск запросов за скидочной статистикой одного пользователя.

### Ваша задача

**До изменения кода** опишите проблемы текущей реализации. Проследите в [методе Get](../../services/profile/internal/infrastructure/adapter/discount/read.go) два одновременных запроса к одному отсутствующему ключу. Какие чтения и записи повторятся? Что увидит третий запрос, если Pricing уже ответил, а фоновый `SET` ещё не завершился? Объясните, как это влияет на нагрузку.

Добавьте **singleflight** в адаптер скидки. Используйте одну группу на экземпляр адаптера и UUID пользователя как ключ. Пока идёт загрузка, запросы того же пользователя должны дождаться её результата или ошибки. Запросы разных пользователей могут выполняться параллельно.

При успешной общей загрузке запустите `setInBackground` один раз. Попадание в Valkey по-прежнему сразу возвращает скидку.

### Проверьте на одном ключе

В одном терминале замедлите чтение из Pricing, чтобы запросы успели пересечься. Дождитесь `ACTIVE`:

```sh
./bin/scooterctl fault profile pricing --method GetCompletedTripsCount --slowdown 50ms --duration 5m
```

Во втором терминале удалите ключ и запустите нагрузку. Выполните обе команды сначала на исходном стенде, затем с singleflight:

```sh
./bin/scooterctl valkey DEL 'user:{704137fe-93b3-4113-8e09-ed1df4d0e0ea}:discount'
./bin/scooterctl load --addr localhost:19090 --method api_gateway.profile.v1.ProfileService/GetDiscount \
  --data '{"userId":"704137fe-93b3-4113-8e09-ed1df4d0e0ea"}' --rps 100 --duration 30s
```

По исходящим логам Profile сравните число вызовов `GetCompletedTripsCount` при промахе. У каждой реплики Profile своя группа. Объясните, сколько одновременных загрузок одного пользователя возможно на стенде с двумя репликами.

### Если одновременно истекли разные ключи

Singleflight объединяет запросы только в пределах одного ключа. Для лавины промахов добавьте jitter к базовому TTL 10 минут и ограничьте общее число параллельных загрузок на реплике.

Снимите задержку в первом терминале через Ctrl+C. Сравните пик обращений к Pricing при фиксированном TTL и после изменений. Каждый прогон начинайте после истечения ключей предыдущей серии.

```sh
./bin/scooterctl load --addr localhost:19090 --method api_gateway.profile.v1.ProfileService/GetDiscount \
  --data-file homeworks/module-10/users.json --rps 100 --duration 12m
```

## 2️⃣ «Десятая поездка есть, скидки нет»

> 💬 **Поддержка:** «У пользователя завершилась десятая поездка. В истории она уже есть, а в личном кабинете всё ещё 0%. Обновление страницы не помогает».

### Воспроизведите на исходном стенде

Rental публикует завершение поездки, и Pricing обрабатывает его. Обновление статистики пока никак не затрагивает ключ в Valkey. Для опыта понадобится первый пользователь с девятью поездками.

Используйте [GetDiscount](http://localhost:18080/docs/index.html#/ProfileService/ProfileService_GetDiscount) и [ReserveRental](http://localhost:18080/docs/index.html#/RentalService/RentalService_ReserveRental) в Swagger UI. Для каждой операции нажмите **Try it out**, затем **Execute**.

1. В `GET /v1/profiles/{userId}/discount` передайте в путь `10000000-0000-4000-8000-000000000001`. На исходных данных ответ содержит 9 поездок и скидку 0%. Проверьте, что фоновый `SET` уже заполнил ключ. Команда вернёт оставшееся время в секундах (сразу после записи — около 600):

   ```sh
   ./bin/scooterctl valkey TTL 'user:{10000000-0000-4000-8000-000000000001}:discount'
   ```
2. В `POST /v1/rentals` вставьте тело бронирования:

   ```json
   {
     "userId": "10000000-0000-4000-8000-000000000001",
     "scooterId": "3499a1fb-030c-47a8-bcd2-0ce8304d6a22",
     "idempotencyKey": "dbf23198-04ec-423e-954e-207a9b716a36"
   }
   ```

3. Скопируйте `rental.id` из ответа в параметр пути `rentalId`. Вызовите сначала `POST /v1/rentals/{rentalId}:start`, затем `POST /v1/rentals/{rentalId}:finish`. Тело обоих запросов одинаковое:

   ```json
   {"userId": "10000000-0000-4000-8000-000000000001"}
   ```

4. В `GET /v1/pricing/trips/{rentalId}` укажите тот же `rentalId` и параметр запроса `userId`. Когда Pricing покажет завершённую поездку, снова вызовите `GetDiscount`, пока TTL ключа положителен. В ответе по-прежнему **9 поездок и 0%**. После истечения ключа тот же запрос вернёт **10 поездок и 10%**.

### Ваша задача

Подключите проактивную инвалидацию по событиям:

1. После обработки завершённой поездки Pricing сохраняет изменение статистики и событие инвалидации в outbox **одной транзакцией**. Используйте реализацию outbox в Rental как образец.
2. Relay публикует событие в `user-discount-invalidate.v1` с UUID пользователя и `stats_version`. Версия относится ко всей статистике пользователя. При чтении Pricing возвращает счётчик и версию из одного снимка.
3. Profile обрабатывает событие и инвалидирует скидку пользователя. Следующий запрос получает свежие данные. Повторные и устаревшие события должны сохранять более новую версию. TTL остаётся запасным механизмом обновления.

### Проверьте результат

Повторите шаги 1–4 для `10000000-0000-4000-8000-000000000002`. Подставьте этот UUID во все запросы и используйте новый `idempotencyKey` при бронировании. После обработки события тот же `GetDiscount` должен вернуть **10 поездок и 10% до истечения исходных 10 минут**. Зафиксируйте, сколько времени прошло с момента, когда Pricing подтвердил завершённую поездку.

**Ответьте:** почему событие должно исходить из Pricing, а не только из Rental? Почему TTL нужен даже с Kafka? Что произойдёт при слишком маленьком TTL и при продлении TTL на каждом чтении?

## 3️⃣ «Сохранил настройку, а после поездки она сбросилась»

> 💬 **Поддержка:** «Включил уведомления о скидке — приложение подтвердило сохранение. Почти одновременно завершилась поездка. Обновляю страницу — уведомления снова выключены».

Расширьте публичный и внутренний контракты **`UpdateProfile`** и схему PostgreSQL Profile, чтобы ручка меняла `discount_notifications_enabled`. Настройка сохраняется в PostgreSQL Profile, затем обновляется её копия в объекте `user:{UUID}:discount`. В этом опыте обработчик события Pricing **помечает скидку в том же объекте устаревшей**, сохраняя настройку уведомлений. Вместе с отметкой он записывает минимальную требуемую `stats_version`; признак актуальности возвращается только после загрузки подходящего снимка Pricing.

Гонка возникает между двумя путями изменения:

1. **Обработчик события на Profile A** читает объект: уведомления выключены. Он готовит инвалидацию скидки, но ещё не сохраняет её.
2. **Ручка UpdateProfile на Profile B** сохраняет включённые уведомления в БД и обновляет кеш.
3. **Обработчик события** записывает подготовленный ранее объект целиком. Вместе с инвалидацией в кеш возвращается старая настройка — «выключено».

В обратном порядке ручка может сохранить настройку, но затереть отметку инвалидации и снова объявить старую скидку актуальной. Данные в БД при этом остаются правильными.

### Ваша задача

Защитите конкурентные записи в обработчике события, в `UpdateProfile` и при фоновом заполнении кеша. Для условного обновления существующего ключа используйте опцию `IFEQ` команды `SET` в Valkey.

### Критерий корректности

После десятой поездки уведомления остаются включёнными при любом порядке записей. Запоздавшее заполнение кеша не возвращает прежнюю скидку 0% после её инвалидации.

## 4️⃣ System design. В 01:00 отказал шард Valkey

В полночь ScooterFlow запустил распродажу. Во время акции главная страница партнёра показывала скидки одних и тех же участников. В кеше находился **миллион ключей**. По выборке запросов за 00:45–01:00 выяснилось, что большую часть чтений дали **100 конкретных ключей**. По карте слотов на момент инцидента все 100 горячих ключей обслуживал один шард.

На графиках перед отказом у этого шарда резко выросли число операций чтения, загрузка CPU и p99, у двух других значения оставались близки к обычным. В **01:00** перегруженный шард перестал отвечать. Пока шло переключение, Profile направил большую часть этих запросов в Pricing. Закончились свободные соединения с PostgreSQL Pricing, запросы стали превышать дедлайн, скидки перестали открываться и у пользователей вне акции.

**Что вы изменили бы до следующей распродажи?** Предложите архитектуру и проследите путь запроса к одному из этих 100 ключей при обычной работе, во время отказа и после восстановления. Объясните, как уменьшится нагрузка на перегретый шард, сколько трафика сможет дойти до Pricing и что увидит пользователь, если его скидка в это время изменится. Назовите графики, по которым дежурный проверит ваши предположения на следующей акции.

Сдайте схему, текстовое описание или оба варианта. Укажите допущения и компромиссы. Для этого задания достаточно проектного решения.
